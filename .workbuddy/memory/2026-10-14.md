## 优化 mod 1（120mm → 500kg）：整条克隆 → 精准字段改写（v1.3.0）
**起因**：用户实测「打击轨迹不符合原版、会超出原版范围」。
**根因**：v1.2.x 的「整条克隆」把 120mm 炮弹记录（272B）整体换成 500kg 的，
连带把**飞行参数**也换了（速度 400→500 / 质量 5000→500 / 阻力 0→0.5 / 引信 0→0.8）。
**用户要的还是**：弹道/攻击保持原版 120mm，只有**落地爆炸**用 500kg（音效/伤害/范围/特效）。

**新做法**：只替换 4 段"爆炸配置"字段（运行时从 500kg 记录读出，绝不写死）：
  `+60 damage_info_type`、`+144 explosion_type_on_impact`、`+152 explosion_delay`、`+156 explosion_type_expire`。
  （本构建：120mm = dmg262 / imp213,176 / delay0 / expire0；500kg = dmg251 / imp193 / delay0.8 / expire277）
10 个"飞行/观感"字段全部保留原版，并加**逐字节 keep-guard**：除这 4 段外任何字节变了就拒绝写入。

**决定性指纹（本次最大收获）**：`audio_trail_event_stop == 3741852184`
  —— 全表 350 条里**唯一**对应两条 120mm 火力网炮弹（type 194/137）；
  同名的凝固汽油弹炮弹（234/238）用的是 `4159288355`，**天然区分**。
  这样就不必写死枚举下标（HE 与凝固汽油弹的 name/clip/物理量/拖尾哈希全都一样，
  仅 damage_info_type / explosion_type_on_impact / audio_* 不同，而前两个都是会漂移的枚举）。
  → 已写进项目硬约定 #11：**"只改爆炸/外观"必须用精准字段改写 + keep-guard，禁止整条克隆。**

**另外修的两个真缺陷**：
1. T8（内存两份表）时序抖动：打完补丁后就不再扫描 → 第二份表可能漏打。
   改为「打完仍把**当前这一轮**扫完再彻底停扫」（`patched` 阶段继续 `scan_pump` 直到 `scan_stopped`）。
2. 后续新增副本没反映到 STATUS → `process_proj_block` 里成功后立即 `flush_status()`。

**验证**：新测试套件 `analysis/test_addon.py` 重写 —— **功能 15 + 变异 10 = 25/25**，
连跑 6 遍稳定；发布正文端到端复测同样 25/25。
变异覆盖：错目标指纹 / 错源指纹 / 拖尾字节序 / 只按名字认记录(会误伤汽油弹) /
整条克隆(被 keep-guard 拦) / 偏移写错 / 把速度写进改写字段 / 漏掉主爆炸 / 去掉回读校验。

### 定位（本次最大的技术收获：换了一张新表）
- "每梭几发" = **`WeaponDataComponentData`** 表里 **`WeaponDataComponent`** 记录的
  **`+140 u32 num_burst_rounds`**。typelib 成员顺序 → `.go` 字段名一一对上（+140 就是 NumBurstRounds）。
- **佐证很硬**：游戏自带 `generated_entity_deltas` 里对 WeaponDataComponent 的 `+140 4字节`
  有 **88 条**覆盖，值分布 {3,4,5,6,7,8,9,…} —— 正是"连发打几发"这种小整数。
- 目标 = **挂载胆汁迫击炮武器 `8536986223483970266` 的 4 个实体**（用 `MountComponentData` 反查）：
  `CCAE5264ACD591B7` / `36AA99CCE5E60146` = 胆汁喷涌虫 Bile Spewer；
  `CC7022FDD172089B` / `6021E22338333D88` = 胆汁医护虫 Nursing Spewer。四者本构建都是 3。
  （关键：**胆汁迫击炮武器实体自己的** `num_burst_rounds` 是 **1** —— 3 只能来自"持有者(角色)实体"，
  这与"怪物只会打 3 发"吻合。用户实机若仍是 3 发，就是这条推断错，见 HANDOVER §8.6 的备选排查路径。）
- ★ **实体组件表布局（写进硬约定 #15）**：`+24 ComponentIndexData[N]`（16B/条：u64 实体哈希 +
  u32 记录号 + u32 0）+ 记录区。**N / 记录数 / stride 全部运行时自标定**（索引区扫出 N 与 maxRec，
  `stride=(size−N×16)/k`，k∈{maxRec+1..maxRec+4} 里"能整除且∈[64,16384]"的唯一解）。
  本构建 = N **730** / **366** 条 / stride **1232**（注意：**maxRec=364 但记录是 366 条**，
  所以不能直接用 maxRec+1 —— 必须留 maxRec+1..+4 的候选带）。
